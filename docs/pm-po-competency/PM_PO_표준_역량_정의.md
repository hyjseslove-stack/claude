# 목적과 적용 범위

PM/PO라면 연차·직급과 무관하게 갖춰야 할 기본 소양 7가지를 정의합니다. 레벨 구분은 두지 않습니다.

- **사용처**: 채용 면접 질문 설계, 신규 입사자 온보딩 기대치 합의, 1:1·평가 대화의 공통 언어
- **판단 방식**: 역량마다 '기대 행동'이 사례로 확인되는지 봅니다. 말로 한 다짐보다 실제 사례와 숫자를 우선합니다.
- **범위 밖**: 팀 리딩(위임·개입, 저성과자 관리, 팀 빌딩)은 리더 포지션 전용 항목이라 이 문서에서는 다루지 않습니다.

# 역량 한눈에 보기

7개 역량은 모두 "문제를 숫자로 잡고, 함께 풀고, 결과까지 책임지고, 구조로 남긴다"는 흐름 위에 있습니다.

| # | 역량 | 한 줄 정의 |
|---|---|---|
| 1 | 문제 정의와 단순화 | 문제를 숫자와 범위로 정의하고, 본질만 남겨 단순하게 푼다 |
| 2 | 오너십 | 산출물이 아니라 결과까지 책임진다 |
| 3 | 경계를 넘는 협업 | 팀·직군의 경계보다 문제 해결과 전체 목표를 앞에 둔다 |
| 4 | 높은 기준 | 기준을 숫자로 세우고, 어떻게 측정할지까지 정한다 |
| 5 | 판단과 실행 속도 | 되돌릴 수 없는 결정은 먼저 확정하고, 나머지는 빠르게 실행한다 |
| 6 | 고객·도메인 이해 | 서비스를 직접 쓰고, 도메인의 구조와 현장을 안다 |
| 7 | 구조화와 확산 | 사람이 아니라 구조로 남겨서, 내가 없어도 돌아가게 한다 |

# 역량별 정의

역량마다 기대 행동 3가지, 하지 않는 것, 확인 질문을 정했습니다.

## 1. 문제 정의와 단순화

문제를 말이 아니라 숫자와 범위로 정의하고, 복잡한 문제에서 본질만 남겨 단순하게 푼다.

- **기대 행동**: 영향 규모(건수·비율·시간·매출)로 문제를 적는다 / 안 할 범위를 먼저 자르고, 핵심 영역부터 쪼개 눈에 보이는 성과를 먼저 낸다 / 증상이 아니라 원인을 파고, 해법은 가장 단순한 형태로 만든다
- **하지 않는 것**: "개선이 필요하다"로 시작하는 기획 / 문제를 풀기보다 기능을 더해서 복잡도를 키우는 것
- **확인 질문**: 지금까지 겪은 가장 복잡한 문제는 무엇이고, 그 본질은 무엇이었으며, 어떻게 단순화해서 해결했나요?

## 2. 오너십

산출물(기획서·출시)이 아니라 결과(지표·매출·고객 변화)까지 책임진다.

- **기대 행동**: 출시 후 지표를 끝까지 확인한다 / 실패는 "제 판단이었다"로 인정하고 재발 방지책을 남긴다 / 미룬 부채는 갚을 계획까지 직접 들고 있는다
- **하지 않는 것**: "개발 일정 때문에", "요청대로 했다"로 마무리 / 주어를 "우리"로 두고 본인 역할을 흐리는 것
- **확인 질문**: 가장 크게 실패한 경험은 무엇이고, 본인의 판단 중 무엇이 틀렸나요? 그 뒤로 무엇을 바꿨나요?

## 3. 경계를 넘는 협업

내 팀의 이상적인 결과보다 전체 목표를 앞에 두고, "그건 우리 팀 일이 아니에요"라고 말하지 않는다.

- **기대 행동**: 상세 기획 전, 초안 단계에서 이해관계자에게 먼저 피드백을 구한다 / 충돌하는 요구는 같은 단위(영향 상품 수·매출·오류율)로 바꿔 비교한다 / 다른 팀이 덜 움직이도록 설계하고, 여러 도메인이 엮이면 공통 KPI를 세운다
- **하지 않는 것**: 완성본을 들고 가서 승인만 받는 것 / 결정권자와 근거를 남기지 않아 같은 논의를 반복하는 것
- **확인 질문**: 이해관계자(영업·개발·운영)를 설득하는 과정에서 가장 어려웠던 지점은 무엇이었고 어떻게 풀었나요?

## 4. 높은 기준

"좋아지자"가 아니라 기준을 숫자로 세우고, 그 숫자를 어떻게 측정하고 추적할지까지 정한다.

- **기대 행동**: 승인 기준과 근거를 함께 제시한다 / 그럴듯한 가설도 실측으로 다시 확인하고, 대상이 너무 많으면 샘플링 검수로 꾸준히 측정한다 / 근거를 (확인)·(증언)·(추정)으로 구분한다
- **하지 않는 것**: "충분히 좋아 보인다"로 오픈 / 측정 방법 없는 목표 / 달성한 숫자를 그대로 받아들이고 더 묻지 않는 것
- **확인 질문**: 목표 수치를 어떻게 정의하고 추적했나요? 그 수치가 낮다고 봤나요, 높다고 봤나요? 그 이유는요?

## 5. 판단과 실행 속도

되돌릴 수 없는 결정(정의·데이터 모델·계약)은 먼저 확정하고, 되돌릴 수 있는 일은 빠르게 내고 실측으로 보완한다.

- **기대 행동**: 비싼 결정은 킥오프에서 확정한다 / 나머지는 MVP로 내고 반복한다 / 우선순위는 "막히면 가장 많은 것이 같이 막히는 일"부터 정한다
- **하지 않는 것**: 모든 걸 완벽히 정하느라 출시를 늦추는 것 / 정의 없이 속도부터 내는 것 / 요청한 팀이 많은 순서로 우선순위를 정하는 것
- **확인 질문**: 가장 큰 장애물은 무엇이었고 어떻게 돌파했나요? 그때 무엇을 포기하고 무엇을 지켰나요?

## 6. 고객·도메인 이해

서비스를 직접 쓰고, 도메인의 구조와 현장(고객·판매자·운영)을 알고 판단한다.

- **기대 행동**: 담당 도메인의 핵심 개념·상태 흐름·원장(SoT)을 자기 말로 설명한다 / 운영 화면과 데이터를 직접 본다 / '동일 상품'처럼 모호한 기준을 판단 원칙(예: 가격에 영향을 주는가)으로 정하고 매뉴얼로 만든다 / 서비스의 개선점을 구체적인 장면으로 말한다
- **하지 않는 것**: 서비스를 써보지 않고 문서로만 기획하는 것 / 현장 예외 케이스를 모른 채 규칙을 정하는 것
- **확인 질문**: 우리 서비스를 써본 적이 있나요? PM 시점에서 개선이 필요하다고 느낀 부분은요? / [어려운 카테고리]에서 동일 상품을 판단하는 기준은 무엇인가요?

## 7. 구조화와 확산

일을 사람이 아니라 구조로 남기고, 내가 찾은 효율화 방법(AI 포함)을 동료에게도 퍼뜨린다.

- **기대 행동**: 의사결정을 근거·날짜·결정자와 함께 기록한다 / 반복 업무는 Runbook이나 자동화로 바꾼다 / AI로 자기 업무를 효율화하고 그 방법을 일반화해 공유한다
- **하지 않는 것**: 담당자 머릿속에만 있는 운영 지식 / 사람을 더 투입해서만 해결하는 것
- **확인 질문**: 사람이 하던 일을 구조나 자동화로 바꾼 사례가 있나요? 그 결과 동료의 일은 어떻게 바뀌었나요?

# 면접 적용 가이드

2026년 2월 27일 Core Catalog PM 1차 인터뷰에서 쓴 질문 15개 중 10개를 표준 역량에 매핑했고, 3개는 리더 전용, 자기소개·역질문 2개는 제외했습니다. 구조화와 확산 질문은 새로 추가했습니다. 지원자 이력이 들어간 자리는 [ ]로 바꿨습니다.

| 역량 | 질문 (템플릿) | 꼬리질문 |
|---|---|---|
| 문제 정의와 단순화 | 지금까지 겪은 가장 복잡한 문제는 무엇이고, 그 본질은 무엇이었으며, 어떻게 단순화해서 해결했나요? | 신규 데이터는 규칙으로 막을 수 있는데, 기존 데이터는 어떻게 정리했나요? |
| 높은 기준 | [품질 지표]를 [목표치]로 달성하셨는데, 이 수치를 정의하고 추적하는 방식이 있나요? | 그 기준은 누가 어떻게 판별하나요? |
| 높은 기준 | [이전 성과 수치]를 낮다고 판단하셨나요, 높다고 판단하셨나요? | 낮았다면 한계의 원인은 무엇이었고, 다음에는 무엇을 다르게 했나요? |
| 경계를 넘는 협업 | [구조 개편 과제]에서 기준은 어떻게 정했고, 이해관계자(영업·개발)를 설득하는 과정에서 어려웠던 지점은 무엇인가요? | 반대한 사람은 누구였고 무엇으로 설득했나요? |
| 판단과 실행 속도 | [생산성 개선 과제]에서 가장 큰 장애물은 무엇이었고, 어떻게 돌파했나요? | 그때 포기한 것은 무엇인가요? |
| 오너십 | [진행 중 과제]는 종료됐나요, 아직 진행 중인가요? | 결과는 어떻게 확인하고 있나요? |
| 오너십 | 현재 겪고 계신 가장 큰 문제(고민)는 무엇인가요? | 그 문제를 풀기 위해 지금 직접 하고 있는 것은요? |
| 고객·도메인 이해 | [어려운 카테고리]에서 동일 상품·동일 카탈로그라고 판단하는 기준은 무엇인가요? | 예외 케이스는 어떻게 처리하나요? |
| 고객·도메인 이해 | 우리 서비스를 직접 써보셨나요? PM 시점에서 개선이 필요하다고 느낀 부분은요? | 그 개선을 한다면 어떤 지표로 확인하시겠어요? |
| 고객·도메인 이해 | 지원하신 배경은 무엇이고, 이 팀에서 구체적으로 어떤 일을 하게 될지 생각해 보셨나요? | 지금 하는 일과 무엇이 같고 무엇이 다른가요? |
| 구조화와 확산 | [검수·운영 업무]를 구조나 자동화로 바꾼 사례가 있나요? | AI는 별도 조직이 하나요, 직접 하나요? |

**리더 포지션에만 추가하는 질문** (표준 역량 범위 밖): 위임과 직접 개입의 기준 / 저성과 팀원 관리 사례 / 하이퍼포머 팀을 만들기 위한 액션과 팀원 피드백

**꼬리질문 원칙**

1. 주어를 확인한다: "우리"가 나오면 "그중 본인이 결정한 것은요?"로 되묻는다
2. 숫자가 나오면 정의와 측정 방식을 묻는다
3. 성과가 나오면 포기한 대안과 그 이유를 묻는다
4. 실패가 나오면 본인 판단의 어느 부분이 틀렸는지 묻는다
